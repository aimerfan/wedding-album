逐一說明

由外往內排列，跟一個請求實際經過的順序相同。

主機外面
L0

賓客手機（瀏覽器／PWA）

做什麼
掃會場 QR code 打開網址，網址裡的活動碼換到一組匿名 token，存在手機裡當作身分。可以加到主畫面，之後像 App 一樣打開。
Service Worker
預先存好前端程式，縮圖與顯示圖用 CacheFirst 存最多 300 張。不碰 /api/ 和原檔，避免手機空間被影片吃光。只在正式憑證下才會註冊，所以本機演練測不到。
設定在
frontend/vite.config.ts
失效時
清除瀏覽器資料就變成新賓客，這是刻意接受的取捨；換手機可用接續碼接回。
L1

網域 + Cloudflare

免費方案網域要付費
網域
印在 QR code 上的那個名字。一定下來就不能換，換了就要重印。
DNS
一筆 A 記錄指向 VPS 的 IP，開橘色雲。開了之後外界查到的是 Cloudflare 的 IP，主機的 IP 不會曝光。
代理與憑證
手機到 Cloudflare 用 Cloudflare 自動發的公開憑證；Cloudflare 到主機用 Origin Certificate（只有 Cloudflare 認得，瀏覽器不認）。模式設 Full (strict)，兩段都加密而且會驗證主機的憑證。
快取
/media/ 和 /assets/ 由 nginx 標成可長期快取，Cloudflare 照著存，同一張照片被一百人看，主機只送一次。index.html、sw.js 標成不快取，改版才推得出去。
限制
免費方案單一請求最多 100 MB、主機要在 100 秒內開始回應。後端的影片上限 95 MB 就是從這裡來的。
失效時
Cloudflare 本身掛掉整站就連不上，這個我們無法控制。刪掉的照片在 Cloudflare 快取裡還會留著，需要手動 Purge。
主機本身
L2

VPS 與防火牆

月費
做什麼
唯一的一台主機，所有程式和資料都在上面。
規格
Ubuntu 26.04（內建 Python 3.14，不必另外裝）· 東京／新加坡／台灣機房 · 2 vCPU · 4 GB · 50～80 GB 硬碟。硬碟估算約 30 GB（3000 張照片 × 5 MB ＋ 200 支影片 × 60 MB），加婚紗照與餘裕。
防火牆
只開 22（SSH）、80（轉到 443）、443。後端的 8000、8001 只聽 127.0.0.1，外面本來就連不到。
登入
只用 SSH 金鑰。
失效時
主機壞掉就全部停擺，而且目前沒有自動備份，照片會跟著沒了。見下面的審閱發現。
L3

nginx

做什麼
主機的大門，所有請求都先到這裡。
分流
  • POST /api/photos → 上傳池。同一個網址的 GET（照片列表）走一般池，靠 map $request_method 判斷。
  • 其他 /api/ → 一般池，30 秒逾時。
  • /media/ → 直接從磁碟送，不經過 Python；影片播放要的 Range 請求 nginx 原生支援。
  • 其他路徑 → frontend/dist/，找不到的都回 index.html（前端路由）。
上傳緩衝
上傳的檔案由 nginx 先完整收下才交給 gunicorn。會場網路慢、傳了三分鐘的手機只佔住 nginx，不佔後端的 worker。這是分池能成立的前提。
大小與逾時
上傳放寬到 100 MB、兩次收到資料間隔最多 120 秒、後端處理最多 150 秒；其他請求限 1 MB。
其他
80 一律轉 443 · JSON／JS／CSS 壓縮 · 補上 heic、mov 的檔案類型。
設定在
deploy/nginx/wedding-album.conf，部署時把 album.example.com 換成實際網域。
L3

systemd

做什麼
管理後端程式的生命週期：開機自動啟動、掛了自動重啟、記錄集中到 journalctl。
三個服務
  • wedding-album-init：跑一次就結束，先建好資料表。另外兩個都依賴它，避免兩池同時建表互撞。
  • wedding-album-api：一般池。
  • wedding-album-upload：上傳池。
身分
以系統使用者 wedding 執行：不能登入、沒有家目錄，只擁有 /var/lib/wedding-album/。
設定在
deploy/systemd/*.service
L4

gunicorn：上傳池與一般池

上傳一般

gunicorn 是正式環境跑 Flask 的伺服器，一個池就是一組 worker 行程。分兩池的理由：HEIC 轉檔、抓影片封面很吃 CPU，如果跟瀏覽共用 worker，上傳高峰時大家滑相簿、按讚都會排隊。分開之後上傳再塞，瀏覽那一池仍然有空的 worker。

上傳池一般池
位址127.0.0.1:8001127.0.0.1:8000
負責只有 POST /api/photos列表、詳情、讚、收藏、祝福、管理…
worker 數3（= 同時處理 3 個上傳）4
逾時120 秒，重啟時等進行中的做完30 秒
其他處理 500 次換新 worker，避免影像處理記憶體越用越多—

worker 數是先抓的，還沒壓測，彩排時看 CPU 與記憶體再調。

L5

Flask app

做什麼
業務邏輯。兩個池跑的是同一份程式，只是 nginx 送進來的請求不同。
身分
活動碼換 token，資料庫只存 token 的 SHA-256。管理員用另一組代碼開通。
上傳
檢查大小與時長 → 算 SHA-256（同一人重送同一檔回傳原本那張）→ 照片轉正方向、產生顯示圖與縮圖；影片用 PyAV 讀長度、抓第一格當封面，原檔不轉檔。中途失敗會清掉已存的檔案。
限流
每人每小時最多 300 個上傳；婚禮後設 UPLOADS_OPEN=false 截止上傳。所有上限都能用環境變數改，重啟就生效。
不做的事
正式環境不送 /media，那是 nginx 的工作。nginx 沒設好會直接 404，不會悄悄拖慢後端。
設定在
backend/app/config.py（預設值）＋ /etc/wedding-album/env（正式值）
資料與設定
L6

SQLite

做什麼
賓客、照片資訊、讚、祝福都在 /var/lib/wedding-album/wedding.db 這一個檔。
多人同時用
WAL 模式：寫入時其他人照樣能讀。兩個寫入撞在一起時後到的最多等 15 秒，不會直接報錯。婚禮規模（幾百人、寫入都很短）SQLite 足夠。
備份
不能只複製 wedding.db（最新資料可能還在 -wal 檔裡），要用 sqlite3 wedding.db ".backup 檔名"。
L6

照片與影片檔

做什麼
/var/lib/wedding-album/media/photos/<id>/ 底下放 original、display、thumb 三個檔。後端寫入，nginx 讀出。
為什麼放這裡
跟程式資料夾 /srv/wedding-album/ 分開，重新部署、刪掉重抓 repo 都不會動到資料。
權限
擁有者 wedding，資料夾 755、檔案 644，nginx 才讀得到。匯入指令要以 wedding 身分跑，否則之後後端刪不掉。
之後
要長期保存再換成 Cloudflare R2（做法 C），只改 storage.py 與 MEDIA_BASE_URL。

設定與機密

env 檔
/etc/wedding-album/env，權限 600：EVENT_CODE（沒設後端不啟動）、ADMIN_CODE、資料庫與照片位置。範本是 deploy/wedding-album.env.example。

/etc/ssl/wedding-album/origin.pem 與 origin.key。私鑰只在 Cloudflare 產生的當下顯示一次。
原則
都不進 git，另外自己記好。

前端建置結果與維運工具

前端
在主機上 npm ci && npm run build 產生 frontend/dist/，nginx 直接送。檔名帶雜湊的 /assets/ 快取一年。
檢查腳本

四條典型請求

第一次掃 QR code

  1. 手機打開 https://網域/?code=活動碼，Cloudflare 回快取的前端或向 nginx 拿。
  2. 前端呼叫 /api/... 加入，nginx 送一般池。
  3. Flask 比對活動碼、建賓客、發 token，寫 SQLite。
  4. Service Worker 註冊，之後可加到主畫面。

滑相簿

  1. 列表 GET /api/photos → 一般池 → 讀 SQLite，回傳照片網址。
  2. 縮圖 /media/.../thumb.jpg：先看手機快取，再看 Cloudflare 快取，都沒有才到 nginx 讀磁碟。
  3. 完全不經過上傳池，上傳再忙也不受影響。

上傳一支影片

  1. 手機傳到 Cloudflare（≤ 100 MB）→ nginx 收完整個檔案（網路慢也只佔 nginx）。
  2. nginx 交給上傳池，Flask 算雜湊、讀長度、抓封面、存檔、寫 SQLite。
  3. 要在 100 秒內開始回應，否則 Cloudflare 會斷線；前端會自動重送，雜湊去重讓它不會重複。

播放影片

  1. 瀏覽器用 Range 請求一段一段拿 /media/.../original.mp4。
  2. nginx 直接從磁碟回應，Python 不參與。
  3. 原檔不進 Service Worker 快取。

審閱發現

架構本身沒有要改的地方。以下是這次逐一檢查時看到、還沒寫進文件或還沒決定的事，依「什麼時候要處理」分類。

購買時

確認 VPS 商有 Ubuntu 26.04 映像

整套設定和演練都建立在 26.04 內建 Python 3.14 上。如果只有 24.04，就要另外裝 Python 3.14，演練結果也不完全適用。下單前先看映像清單。

購買時

備份：建議直接勾 VPS 商的自動備份或快照

目前唯一沒解決的高影響風險。多數 VPS 商的自動備份是月費加兩成左右，購買時勾選就好，不用寫任何東西，比婚禮前臨時加 rsync 省事。婚禮後照原計畫再手動備份一次。

購買時

網域字尾：Cloudflare 不賣 .tw

Cloudflare 的網域註冊不支援 .tw、.com.tw。想用 .tw 就要在台灣的註冊商買，再把 NS 改到 Cloudflare（生效可能要幾小時）。用 .com 等字尾直接在 Cloudflare 買最快。

購買時

流量額度

上傳約 30 GB 進主機；送出有 Cloudflare 快取擋掉大部分，但影片原檔會一直送。選每月至少 1 TB 流量的方案就不必擔心，大多數方案都有。

部署時

防火牆與 SSH 的指令還沒寫進 deploy/README

docs/deploy/README.md 把「防火牆只開 22、80、443」「能用金鑰登入」列為過關條件，但第一次部署的 1～10 步沒有對應指令。要補上 ufw allow OpenSSH、ufw allow 80,443/tcp、ufw enable，以及關閉 SSH 密碼登入。VPS 商若有網頁版防火牆，設在那邊也可以。

部署時

加 2 GB swap 當緩衝

7 個 worker 平時各約 100 MB；上傳池轉一張 iPhone 4800 萬畫素 HEIC 時單一 worker 可能衝到數百 MB。4 GB 應該夠，但加一點 swap 可以避免高峰時被系統直接砍掉行程。

婚禮前一天

暫停自動更新

Ubuntu 預設會自動裝安全更新，可能順帶重啟服務。10/16 手動 apt upgrade 完、彩排沒問題後，暫停 unattended-upgrades 到婚禮結束。

可不做

主機 IP 直連可以繞過 Cloudflare

知道 IP 的人可以略過 Cloudflare 直接連 443（瀏覽器會報憑證錯誤）。IP 不會從 DNS 曝光，婚禮規模風險很低。要堵的話讓防火牆的 80／443 只放 Cloudflare 的 IP 段，代價是之後無法用 IP 直接測。

可不做

Cloudflare 對影片流量的條款

已列在風險表、仍未查證。婚禮一次性、幾百人的規模應該不會被注意，真的被限制時再升級做法 C（影片放 R2）。
